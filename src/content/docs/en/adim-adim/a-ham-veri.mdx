  <Step title="What is raw data?" stage="a">
    A company's knowledge lives in PDF, Word or HTML files. We call the text taken from these files **raw data**. Its content is right. But it carries traces of the file: page headers, page numbers, menus.
  </Step>
  <Step title="Our raw data: hr-leave.md" stage="a">
    We skip the text extraction in this workshop. Each file in `corpus/` looks like text from a PDF. We added page headers, page numbers and broken lines on purpose. So there is something real to clean.
  </Step>
  <Step title="Two steps, no model" stage="a">
    `1-load.ts` reads the file. It separates the block of labels at the top from the main text. `2-clean.ts` cleans the text. No model runs in either step, only our own code.
  </Step>
  <Step title="The block at the top: metadata" stage="b" phase="1">
    Between two `---` lines, the document describes itself. It gives its `id`, `edition` and department. It says who may read it (`access`) and its language (`lang`). We call this <Term id="metadata">metadata</Term>. `1-load.ts` stores it.

    <Now n="1">Run `npm run step -- 1`, then open `data/1-docs.json`. Which field shows that only HR may read `hr-salary-bands`?</Now>
  </Step>
  <Step title="Does a real PDF have this block?" stage="b" phase="1">
    No. In a real project, another system keeps the edition and read access. It is the system that holds the document: SharePoint, Confluence or an archive. We wrote them at the top to keep everything in one file.
  </Step>
  <Step title="Metadata becomes a filter later" stage="b" phase="1">
    `hr-salary-bands` has `access: hr-only`. Only HR may read it. We read the label now. We check it when a question comes in (page E). If the record has no label from the start, there is nothing to filter later.
  </Step>
  <Step title="The text below: traces of the PDF" stage="b" phase="2">
    hr-leave looks like text from a 4-page PDF. Each page starts with the same header and a confidentiality line. Each page ends with a number like `Page 1 of 4`. These lines are not content. We call them noise.
  </Step>
  <Step title="Why is noise a problem?" stage="b" phase="2">
    The header line repeats on every page. When we split the text, it lands in many chunks. Then many chunks share this line, so they look more alike. That can make them harder to tell apart.
  </Step>
  <Step title="Broken lines, too" stage="b" phase="3">
    The page width also broke sentences apart. "special" ends one line, and "leave" starts the next. A person reads this fine. But a program that works line by line sees two separate parts.
  </Step>
  <Step title="Cleaning: 4 rules and a line joiner" stage="b">
    `2-clean.ts` drops the noise with 4 rules (regex). They catch the page header and the English confidentiality line. They also catch page numbers in English and Turkish. Then it joins the broken lines. Headings, tables and blank lines stay.

    <Now n="2">In `src/steps/2-clean.ts`, comment out the first rule of the `NOISE` list. Run `npm run step -- 2`. The `hr-leave` line should show −8 noise lines. Then turn the rule back on and run `npm run step -- 2` again.</Now>
  </Step>
  <Step title="Result: raw data in, clean text out" stage="b">
    In the 8 documents, 1078 lines went down to 512. Of the 566 removed lines, 74 are noise. The rest are joined lines and extra blank lines that the cleaning deleted. Both steps took a few milliseconds.
  </Step>
  <Step title="Inside 1-load.ts: corpus → 1-docs.json" stage="c" phase="1">
    No classes. Each step is one file, written with plain functions. `npm run step -- 1` runs `src/steps/1-load.ts`. It reads 8 files and writes 8 records to `data/1-docs.json`.
  </Step>
  <Step title="Inside 2-clean.ts: 1-docs.json → 2-clean.json" stage="c" phase="2">
    `2-clean.ts` doesn't run `1-load.ts`. It reads what `1-load.ts` wrote: `data/1-docs.json`. It puts the clean text into the `text` field. It copies the metadata as it is and writes the result to `data/2-clean.json`.

    <Now n="3">Read the section "Where does the leftover noise go?" below. Then write the `turkishConfidential` rule. Check: `npm run step -- 2`. The `it-security` line should show −12 noise lines, not −8.</Now>
  </Step>

## Where does the leftover noise go?

The Turkish document (`it-security`) has the line `GİZLİ – Yalnızca şirket içi kullanım içindir` on every page. In English, it means: confidential, for internal use only. No rule removes this line. In the log, `it-security` shows −8. Its 4 page headers and 4 page numbers are gone. Its 4 confidentiality lines stay. The leftover noise doesn't go away. With the split method of page B, it becomes a chunk named `it-security@2025#0`. That chunk holds only the document title and this line. It has no real content. But it gets a vector and a place in the store, like any other chunk. This is the problem from "Why is noise a problem?", in one chunk.

## Common questions

<FAQ q="Why is edition written in quotes?">
So it stays text. The filter compares text: the text `"2025"` doesn't match the number `2025`. The quotes stop a YAML reader from turning the value into a number. Our small reader takes every value as text anyway.
</FAQ>

<FAQ q="What if a cleaning rule deletes real content by mistake?">
The anchors stop that. Each rule is tied to the start and the end of the line (`^` … `$`). So a line goes only if the whole line matches the pattern. Keep the anchors in your `turkishConfidential` rule too. It must not delete `Gizli veriler şifrelenmelidir.`, a normal Turkish sentence about confidential data.
</FAQ>

<Takeaway>You can't search well in dirty text.</Takeaway>
