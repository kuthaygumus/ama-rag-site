  <Step title="What is in a record?" stage="r">
    Step 5 writes each chunk to Chroma as one record. A record has an id, an embedding (the vector), a document (the text) and metadata.

    <Now n="1">`podman compose ps` should say `healthy`. If not, run `podman compose up -d`.</Now>
  </Step>
  <Step title="The vector: for search" stage="r" phase="1">
    Search works on the vector. It finds the records closest to the question. The vectors come from step 4, already computed.
  </Step>
  <Step title="The text: for the model" stage="r" phase="2">
    You can't get a sentence back from 1024 numbers. The search uses the vector, but the prompt gets the text. So the record carries both. The vector finds, and the text tells.
  </Step>
  <Step title="Metadata: for filters" stage="r" phase="3">
    Metadata holds labels like `edition`, `access` and `docId`. We read these labels on page A. Step 6 says: only edition 2025, only documents open to all. Chroma applies this filter inside the search.
  </Step>
  <Step title="Brute force: check them all" stage="a">
    For every question, the JSON store computes the cosine with every vector. Then it sorts them. The result is exact, but the work grows with the number of chunks. This method is called <Term id="bruteforce">brute force</Term>.

    <Now n="2">Run `npm run step -- 5 --store json`, then open `data/store.json`.</Now>
  </Step>
  <Step title="Vector DB: check the neighbors" stage="a">
    Chroma builds a graph index called <Term id="hnsw">HNSW</Term>. It links each vector to its neighbors. A search starts at one point. It jumps from neighbor to neighbor toward the question. It visits only a small part of the graph.

    <Now n="3">Run `npm run step -- 5`.</Now>
  </Step>
  <Step title="The cost: approximate" stage="a">
    This kind of search is called <Term id="ann">ANN</Term>: approximate nearest neighbor. It almost always finds the closest ones, but there's no guarantee. You lose a little accuracy and gain speed. The index settings set this balance.

    <Now n="4">In Bruno, pick the `local` environment. Send the requests in the `01-chroma` folder in the order the box lists. Find the `hnsw` settings in `collections`.</Now>
  </Step>
  <Step title="Did our ranking change?" stage="a">
    Same question, two stores. JSON and Chroma return the same top 5 ids, in the same order. With 60 records, the approximation doesn't show. The speed gain doesn't show yet either. Both show with millions of records.

    <Now n="5">Run `podman compose down`, then `podman compose up -d`. In Bruno, send `collections` first, then `count`.</Now>

    <Now n="6">Run `npm run question`. The HOW line now says `chroma store`. Is the answer still 22?</Now>
  </Step>

## The four jobs of a vector DB

- **Add / update.** Writing to the same id (upsert) replaces the old record. Our `replaceEdition` first deletes the records of that edition, then adds the new ones. So running step 5 twice doesn't create duplicate records.
- **Delete.** With a `where` condition. Ours is `{ edition }`.
- **Filter.** Also with `where`. `toWhere()` turns our filter into Chroma's format (page E).
- **Keep.** The data survives when the container stops. `compose.yaml` writes it to a volume.

## `podman compose up`, line by line

The command we ran at the start of the day reads this file:

<RepoCode file="compose.yaml" />

- `image: docker.io/chromadb/chroma:1.5.9`. The version is pinned. Everyone gets the same Chroma and the same API.
- `ports: "8000:8000"`. Chroma's HTTP API is on `localhost:8000`. Our code and Bruno both connect here.
- `volumes: chroma-data:/data`. The records live in a named volume, not inside the container. `podman compose down` keeps the data. `down -v` deletes it.
- `ANONYMIZED_TELEMETRY: "false"`. Chroma sends no usage statistics out.
- `healthcheck`. Every 5 seconds, it checks `/api/v2/heartbeat`. If `podman compose ps` says "healthy", Chroma is ready.

## Common questions

<FAQ q="Chroma, pgvector or Qdrant?">
All three store the same three things: the vector, the text and the metadata. The differences are in how you run them. If you already use Postgres, pgvector adds no new system. They differ in scale, in how well they filter, in hybrid search and in managed hosting. We chose Chroma because it is one container, and Bruno can read its HTTP API.
</FAQ>

<FAQ q="Can't Chroma do the embedding itself?">
It can. We turned that off and made the vectors ourselves with Ollama. So the model name is written in one place, and ingest and questions go through the same model.
</FAQ>

<FAQ q="Chroma returns a distance, not a score, right?">
Yes. In cosine space, distance = 1 − cosine similarity. Our code turns it back with `score: 1 - distance`. So JSON and Chroma scores are on the same scale, and we can put them side by side.
</FAQ>

<FAQ q="What do the HNSW settings change?">
Two things: how many neighbors each node links to, and how many candidates a search visits. More means more accurate and slower. Today we use the defaults. We didn't measure other settings.
</FAQ>

<Takeaway>Embedding turns meaning into coordinates. A vector DB searches those coordinates fast.</Takeaway>
