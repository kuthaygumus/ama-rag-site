## Settings

| Setting | Ours | When you raise it | Did we measure it here? |
|---|---|---|---|
| Chunk size | section: 695 characters on average, 60 chunks · fixed: 300 characters, 138 chunks | more tokens in the prompt, fewer vectors | Yes: hit@1 is 0.526 with fixed (10 of 19 questions) and 0.842 with section (16) ([Measuring quality](/en/uretim/kaliteyi-olcmek/)) |
| k (candidates the retriever returns) | 5 | one more LLM call per candidate in rerank; the prompt still gets 3 chunks | No: try it yourself with `--k 10` |
| Chunks in the prompt | 3 | more prompt tokens | 3 chunks = 976 prompt tokens (question of the day) |
| Rerank | on | turn it off: the 5 calls go away, and the vector score sets the order | Partly: for the question of the day, the answer is 22 both ways. For q02, the right section is at rank 5 by vector score. With rerank on, the answer is right. With rerank off, we didn't measure it. |
| Model size | gemma3:4b | more RAM and more time | No: we measured time only with gemma3:4b |
| Embedding cache | on | none | Yes: 60 of 60 vectors from the cache, step 4 = 52 ms |
| Incremental ingest | `replaceEdition` per edition | none | Yes: 2026 added, 120 records in the store, 2025 untouched |

## The bill: a formula without prices

Prices change from provider to provider, so here is a formula, not a number. With an API model, the cost is about this:

> **daily cost = queries/day × (answer prompt + 5 × rerank prompt + output tokens) × unit price**
> **+ one-time embedding at ingest** (only the changed edition; the cache never embeds the same text twice)

- Most providers charge different prices for input and output tokens. Split the formula in two and calculate each part.
- The terms we measured, for the question of the day: answer prompt 976 tokens, output 21 tokens. We don't log the tokens of the rerank prompts. Each one carries the question and one chunk.
- On your own server (self-host), GPU hours take the place of the unit price. You need enough capacity for N questions times 6 calls at the same time, with no waiting.

## Common questions

<FAQ q="Should we buy a faster vector DB?">
Not for this. In this run the vector DB search took 7 ms. Rerank and answer together took 2096 ms (1441 + 655). The bottleneck is the calls to the model. With millions of vectors, search gets expensive too. That is what the index on page D is for.
</FAQ>

<FAQ q="Should we turn rerank off to save time?">
Only if the eval says so. Time and accuracy depend on the same setting: see the Rerank row in the table above. A faster option is a small reranker model trained for this job, a cross-encoder. We didn't measure it.
</FAQ>

<FAQ q="Can we cache the answers too?">
Yes. The same question, the same sources, temperature 0 and a fixed seed give the same answer on the same machine. So you can store the answer. The key needs three parts: question + edition + access scope. Without the scope in the key, the cache can give an employee the salary answer that HR got. When you ingest a new edition, delete the cache for that edition. This repo has no answer cache.
</FAQ>

<FAQ q="Is a bigger model better?">
Only the eval can tell. A bigger model is slower and needs more RAM. On this site we measured times only with gemma3:4b. To change the model, copy `env.example` to `.env` and uncomment the `CHAT_MODEL` line. Then run `npm run eval -- --answers`.
</FAQ>

<Takeaway>Time and cost are not in the search. They are in every model call and every token.</Takeaway>
