  <Step title="What the name means">
    <Term id="rag">RAG</Term> = Retrieval-Augmented Generation. The three words are three jobs that run in order: find, add, write.
  </Step>
  <Step title="R · Retrieval: find" phase="1">
    We search for the question among chunks made from the documents beforehand. The search picks the few most relevant ones. Here, two files do this: `6-retrieve.ts` (search) and `7-rerank.ts` (<Term id="rerank">rerank</Term>).
  </Step>
  <Step title="A + G · add and write" phase="2">
    The chosen chunks get numbers and go in front of the question. Rules go on top. The model writes the answer from this input and adds the source number. Both jobs are in one file, `8-answer.ts`.
  </Step>

    <p class="key">RAG finds relevant chunks, adds them to the prompt, and the model answers from them.</p>

## What does it solve?

| Problem | What RAG does | Where we see it today |
|---|---|---|
| **Private data** | On every question, it puts company documents the model never saw in front of it | [Without RAG / with RAG](/en/neden-rag/ragsiz-ragli/) |
| **Fresh data** | When a new edition arrives, re-ingest it. No training is needed | [When the data changes](/en/adim-adim/veri-degisince/) |
| **Citing sources** | The answer says which chunk it came from, with `[1]` | [F · Generating the answer](/en/adim-adim/f-cevap/) |
| **Access control** | A filter keeps HR-only documents out of the search | [E · Retrieval and reranking](/en/adim-adim/e-retrieval-rerank/) · [Security](/en/uretim/guvenlik/) |
| **Made-up answers** | You can design it to say "I don't know" when the sources don't have the answer | [F · Generating the answer](/en/adim-adim/f-cevap/) |

## What doesn't it solve?

- **Style and format.** How the model talks is not RAG's job. That is a job for the prompt or for fine-tuning.
  The second way changes the model. It is on the next page: [RAG or fine-tuning?](/en/neden-rag/rag-mi-fine-tune-mu/)
- **Math.** The model is still a language model. It can make mistakes when it calculates with the numbers in the
  sources. We didn't measure this today.
- **Bad data.** A wrong, old or conflicting document gives a wrong answer, even when the search finds it.
- **Reading mistakes.** Even with the right chunk in front of it, the model can read the wrong row. More on this:
  [Limits and RAG variants](/en/her-derde-deva/sinirlar-ve-turler/).

What we build today is the simplest form of RAG (naive RAG), plus rerank. Other variants, and the mistake each one
fixes: [Limits and RAG variants](/en/her-derde-deva/sinirlar-ve-turler/).

## Common questions

<FAQ q="Does RAG mean a vector DB?">
No. The find step can also be a keyword search, an SQL query or an API call. Vector search is common because it
searches for meaning, not words. We measure how well it searches on the [C · Embedding](/en/adim-adim/c-embedding/)
page.
</FAQ>

<FAQ q="Is RAG a library or a product?">
No. It is a setup, a design pattern. Today we write every step ourselves, in plain TypeScript. Frameworks
package the same steps. When you build the steps by hand once, you see what is inside a framework.
</FAQ>

<Takeaway>RAG doesn't change the model. It changes what we give the model.</Takeaway>
