  <Step title="The task">
    The model looks at three features of an animal. Then it says cat or dog. Each feature has a weight. A positive weight pushes the answer toward cat, a negative one toward dog. The model is half trained. It doesn't know yet how much barking matters (−0.1).
  </Step>
  <Step title="The prediction">
    A husky comes in. It has pointy ears and a long nose, and it barks. The model adds up the three weights: +0.8 − 0.2 − 0.1 = +0.5. The score is positive, so the answer is "cat". That is wrong. A husky is a dog.
  </Step>
  <Step title="A small change">
    The mistake was the push toward cat. So we move each weight 0.1 toward dog: +0.7, −0.3, −0.2. The new score is +0.2. The answer is still wrong, but it moved the right way.
  </Step>
  <Step title="Once more">
    We make the same fix once more. The score is now −0.1, and the answer is "dog". A plain cat with only pointy ears still gets +0.6. So it is still a cat. Small steps taught the new answer without breaking the old ones.
  </Step>
  <Step title="Why small steps?">
    What if each weight moves 1.0 at once? The husky is fixed. But the pointy-ear weight drops to −0.2. Now the plain cat gets "dog". The step size is called the learning rate. Ours is 0.1. Moving every weight a little toward a smaller error is gradient descent.
  </Step>
  <Step title="Language models and fine-tuning">
    A language model runs the same loop. Its question is "which token comes next?" Our model has about 4 billion weights. Fine-tuning takes a ready model and runs these small steps on your own examples.
  </Step>

  <Step title="RAG: a short, flat road" phase="1">
    You start with a ready model. The only bump is to prepare the documents once: the <Term id="ingest">ingest</Term>. The flag sits at ground level. The knowledge is not inside the model. It is in front of it. If a document changes, you ingest it again. The model never changes.
  </Step>
  <Step title="Fine-tuning: a long climb" phase="2">
    The other way is to train the model again: <Term id="finetune">fine-tuning</Term>. You prepare example pairs and train the model on a GPU. Then you measure it. If it fails, you start over. It is a long road. If what you teach changes, you climb again.
  </Step>
  <Step title="Why is the flag so high? What does it teach?" phase="3">
    The climb changes the weights. Fine-tuning teaches behavior best: tone, format, company terms. You don't repeat them in every prompt.

    <strong class="turn">BUT</strong> facts don't get into the weights reliably. A pattern from thousands of examples stays. A number from a few examples leaves only a small trace. The model remembers the fact only in part. It can mix up similar numbers and can't cite a source.
  </Step>
  <Step title="Together">
    They are not rivals. You can also use them together. Today we build only RAG, because our knowledge changes. It is the policies, and they get a new edition every year.
  </Step>

## Side by side

| | RAG | Fine-tuning |
|---|---|---|
| **What does it change?** | The input to the model. The model stays the same | The model's weights |
| **What it teaches best** | Facts: what the policy says, how many days | Behavior: tone, format, terminology |
| **Facts** | Reads them from the text and cites the source: `[1] hr-leave §3` | Not reliable: it can remember only part, mix facts up, and it can't cite a source |
| **When the data changes** | Re-ingest. The model stays the same ([When the data changes](/en/adim-adim/veri-degisince/)) | Train again: data, GPU, measuring |
| **Cost per question** | High: the model reads the sources too (976 prompt tokens for the question of the day, 37 without sources) | Low: only the question |
| **Access control** | Metadata filter: who can see what | None: any user can ask for what is stored in the weights |

The token counts in the RAG column come from the output of `npm run step -- 8` and `npm run step -- 0`.
We didn't measure the fine-tuning column today. Its rows come from general experience.

## When is fine-tuning the right choice?

When you want to teach a **behavior** that doesn't change:

- **Format**: every answer must come in the same template or the same JSON shape.
- **Tone**: the company's style. Short, formal, in a set language.
- **Terminology**: internal abbreviations and product names. A glossary the model must use correctly.

Try the prompt first. Most behavior needs only one rule line. Think about fine-tuning when the rules get too

## Common questions

<FAQ q="What is LoRA?">
A cheap way to fine-tune. The model's main weights stay frozen, and you train a small add-on next to them. It
cuts cost and time. It doesn't change the answer to "what does it teach?" The answer is still behavior.
</FAQ>

<Takeaway>RAG for facts that change, fine-tuning for behavior that doesn't.</Takeaway>
