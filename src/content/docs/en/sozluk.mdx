## A

<h3 id="abstain">Abstain (saying "I don't know")</h3>

The model says "I don't know" on purpose when the answer isn't in the sources. This doesn't happen by itself. You design it with a rule in the prompt. Our rule uses this sentence: "This is not in the policies." The code finds this answer by searching for part of that sentence. If the model says no in its own words, the code misses it. With the rule off, it wrote: "No, this policy does not cover stock options [1]."

<h3 id="access">Access filter</h3>

A filter inside the search. Each chunk carries the `access` label of its document. The search returns only the chunks the asker may read. In this repo, the asker's access list is a toggle in `6-retrieve.ts`. It protects the data, not the answer.

<h3 id="agentic">Agentic RAG</h3>

RAG where the model runs the search. It splits the question into parts and searches for each part. It checks "is this enough?", then it answers. It is for questions that need several documents. The cost: many calls and more time. This repo doesn't have it.

<h3 id="ann">ANN (approximate nearest neighbor)</h3>

A search that uses an index and visits only the nearby vectors, not every vector one by one. It loses a little accuracy. But it stays fast, even on millions of vectors.

<h3 id="answer-check">Answer check</h3>

Code that reads the answer after the model writes it. It drops every sentence that has no source number [n]. The sentence "This is not in the policies." stays. In this repo, it is the `CHECK_ANSWER` toggle in `8-answer.ts`. It is off by default.

## B

<h3 id="bge-m3">bge-m3</h3>

The embedding model of this course. It turns every text into a vector of 1024 numbers. It puts English and Turkish in the same space. That is why our English questions can find sections of the Turkish document. It runs locally in Ollama.

<h3 id="bi-encoder">Bi-encoder</h3>

A model that turns the question and the chunk into vectors separately. Vector search works this way. It is fast, because each chunk's vector is computed once, at ingest.

<h3 id="bm25">BM25</h3>

The classic keyword search score. It looks at how often the words of the question appear in a document. It is the keyword half of hybrid search.

<h3 id="bruno">Bruno</h3>

A desktop app for sending HTTP requests by hand. In this course we use it to look inside Ollama and Chroma. The terminal runs the pipeline.

<h3 id="bruteforce">Brute force</h3>

Comparing the question with every vector in the store, one by one. The result is exact, but the work grows with the number of vectors. Our JSON store works this way.

## C

<h3 id="catchup">Catch-up</h3>

`npm run catchup -- N` sets every toggle back to its default and empties the `data/` folder. It also resets the vector store. Then it runs steps 1 to N again. The functions you wrote stay as they are. `N = 0` runs no step: you go back to the start of the day.

<h3 id="chroma">Chroma</h3>

The vector DB of this course. It runs as a container in Podman. It stores each record with its vector, its chunk text and its metadata.

<h3 id="chunk">Chunk</h3>

A piece of a document. The search finds these pieces, not whole documents. The model gets only the few chunks that are chosen for the prompt (3 in our setup).

<h3 id="chunking">Chunking</h3>

Splitting a document into chunks. Where you cut decides what the search can find. The fixed chunker cuts every 300 characters. The section chunker cuts at every `## n.` heading. You write the paragraph chunker on page B.

<h3 id="kaynak">Citation</h3>

Writing which chunk each fact in the answer came from, with a number like `[1]`. With it, you can check the answer. But a source alone doesn't make the answer right: see [Hallucination](#hallucination).

<h3 id="context">Context window</h3>

The most tokens a model can read at one time. The prompt, the sources and the answer must all fit in it. Our setting is 8192 tokens (`num_ctx`).

<h3 id="cosine">Cosine similarity</h3>

How much two vectors point the same way. 1 means the same direction, so the same meaning. Unrelated texts still score well above 0: our unrelated pair scored 0.503. Our search scores use this measure.

<h3 id="cross-encoder">Cross-encoder</h3>

A model that reads the question and the chunk together and gives one relevance score. It is used as a reranker. Our reranker is not a model trained for this job. We ask the chat model to score each chunk for the question, from 0 to 10.

## D

<h3 id="dense-sparse">Dense and sparse vectors</h3>

In a dense vector, every dimension has a value and carries meaning (embedding). A sparse vector is mostly zeros, and each dimension is one word (keyword search).

<h3 id="dot">Dot product</h3>

Multiply two vectors number by number, then add up the results. For vectors of length 1, it gives the same result as cosine. bge-m3 makes vectors like this.

## E

<h3 id="edition">Edition</h3>

The year of a policy: 2025 or 2026. It is stored as metadata. By default, the search looks only at the latest edition. Why filter? With every edition in the search, the 2026 and 2025 leave tables score almost the same: 0.619 and 0.614.

<h3 id="embedding">Embedding</h3>

A text turned into a list of numbers (a vector). Texts with close meanings get close numbers. The embedding model decides what counts as close.

<h3 id="eval">Eval</h3>

Scoring the system with questions whose answers we know. Ours is `npm run eval`. For retrieval it gives hit@1, recall@k and MRR. With `--answers`, it also checks the answers.

## F

<h3 id="isaretli-kaynak">Fenced source</h3>

Each source in the prompt starts with a start marker, `<<<SOURCE n: document title>>>`. It ends with an end marker, `<<<END SOURCE n>>>`. The markers show where the text from a document starts and ends. They didn't stop the injection. The rules in the prompt didn't stop it either. A small check in code, run on the answer, removed the request: see [Prompt injection](#injection).

<h3 id="finetune">Fine-tuning</h3>

Training a ready model a little more with your own examples. It writes knowledge into the weights. To change that knowledge, you train again. It is good for teaching behavior: tone, format, terms.

<h3 id="front-matter">Front matter</h3>

The fields between the `---` lines at the top of a Markdown file. Ours are `id`, `title`, `edition`, `department`, `access` and `lang`. The load step turns them into metadata.

## G

<h3 id="gemma3">gemma3:4b</h3>

The chat model of this course, with about 4 billion parameters. It runs locally in Ollama. It writes the answer and also gives the rerank scores.

<h3 id="goldset">Gold set</h3>

A list of questions with known answers. Each question has the right section and the expected value. Ours is `eval/gold.jsonl`, with 23 questions. We score every version of the system with the same list.

<h3 id="graphrag">GraphRAG</h3>

At ingest, it builds a graph of the things in the documents and their links. At question time, it follows those links. It helps when the answer is in the links between documents. It is the most expensive kind of RAG.

## H

<h3 id="hallucination">Hallucination</h3>

The model makes something up and says it with confidence, like a fact. RAG reduces this but doesn't end it. On the fixed-chunk run, the model answers "at most 7 working days" with a source [1]. The 7 is in the policy, but it is another rule: the longest block of leave in peak season. The right table row never reached the prompt.

<h3 id="hit1">hit@1</h3>

Is the first result right? 1 if yes, 0 if no. Then we take the average over all questions.

<h3 id="hnsw">HNSW</h3>

An [ANN](#ann) index that many vector DBs use. It links the vectors to their neighbors in a graph. Chroma uses it.

<h3 id="hybrid">Hybrid search</h3>

Keyword search combined with vector search. It helps with words you search for exactly, like codes, numbers and names. It doesn't help across languages, because two languages share no words.

<h3 id="hyde">HyDE</h3>

The model first writes an imagined answer to the question. Then we search with that answer, not with the question. An imagined answer sounds more like the documents than the question does. The cost is one call per question.

## I

<h3 id="ingest">Ingest</h3>

The preparation that makes documents searchable: load, clean, chunk, embed, store. It runs once, and again when a document changes. Ours is `npm run ingest`.

## L

<h3 id="l2">L2 distance</h3>

The straight-line distance between two vectors. Smaller means closer. For vectors of length 1, it gives the same ranking as cosine.

<h3 id="ledger">Ledger</h3>

`npm run question` saves every answer to `.cache/question-ledger.jsonl` and shows the list. It holds every answer the question of the day gets during the day.

<h3 id="llm">LLM</h3>

Large language model: a model that predicts the next part of a text, one token at a time. Everything it knows is in its weights. RAG gives it sources in the prompt.

<h3 id="judge">LLM-as-judge</h3>

Asking another language model to score an answer. For example: "Is every claim in this answer in the sources?" The judge can be wrong too. Check its scores as well.

<h3 id="lora">LoRA</h3>

A cheap kind of fine-tuning. It doesn't train all the weights of the model. It trains a small set of extra weights added next to them.

## M

<h3 id="metadata">Metadata</h3>

The labels on a chunk, next to its text. They say which document, which edition and who may read it. The search uses them as filters. The filter runs inside the search.

<h3 id="mmr">MMR</h3>

A method that picks results by two things: closeness to the question and difference from each other. It stops chunks that say the same thing from filling the prompt.

<h3 id="mrr">MRR</h3>

For each question, take 1 divided by the rank of the first right result. Then average over all questions. 1.0 means the right result is always first.

<h3 id="multiquery">Multi-query</h3>

The model rewrites one question in a few different ways. Each rewrite gets its own search. Then we merge the results.

## N

<h3 id="norm">Norm (vector length)</h3>

The length of a vector. bge-m3's vectors have length 1. `4-embed.ts` prints it in its log.

## O

<h3 id="ollama">Ollama</h3>

A tool that runs language models on your laptop. In this course, both the embedding model (bge-m3) and the chat model (gemma3:4b) run in it. The data never leaves the machine.

## P

<h3 id="paraphrase">Paraphrase</h3>

Saying the same thing with different words. One text says "holiday", the other says "annual paid leave". Keyword search misses this. Embedding search finds it, but in our test question ("How much holiday do I get? I started here 4 years ago.") the right section came only 5th. Rerank then moved it to 1st, and the answer was right: 18 working days [1].

<h3 id="parentchild">Parent-child</h3>

Search with small chunks. Then give the model the bigger chunk around each one. Small chunks are easy to find. Big chunks are easy to read.

<h3 id="pca">PCA</h3>

Bringing 1024 dimensions down to 2, so we can draw them. It finds the two directions where the chunks differ most. Most of the information is lost, but the rough layout stays. `npm run map` draws with it.

<h3 id="pii">Personal data (PII)</h3>

Information that identifies a person: name, employee number, phone, email. You mask it when a document enters the system, before it becomes a vector. The logs follow the same rule. This repo has no masking.

<h3 id="podman">Podman</h3>

A tool that runs containers. We start Chroma with `podman compose up -d`.

<h3 id="prompt">Prompt</h3>

The full text the model gets. Ours has the rules, then the fenced and numbered sources, then the question. The `--prompt` flag shows it as it is.

<h3 id="injection">Prompt injection</h3>

Hiding an instruction inside a text the model reads. In RAG, that text can be a document, like our meal card announcement. In our run, the model obeyed it. The answer asked for the employee number and password. The rules in our prompt didn't stop it. A check in code, after the model, removed the request ([Security](/en/uretim/guvenlik/)).

## R

<h3 id="rag">RAG</h3>

Retrieval-Augmented Generation. Before the model answers, we find the relevant chunks. We put them in front of the model. The model doesn't change. Only its input changes.

<h3 id="ragfusion">RAG-fusion</h3>

It works like multi-query, but it merges the result lists with [RRF](#rrf). A chunk near the top of several lists moves to the front.

<h3 id="recallk">recall@k</h3>

How many of the right sections get into the top k results. It ignores the rank. Being in the list is enough.

<h3 id="rrf">Reciprocal rank fusion (RRF)</h3>

Merging several result lists by scoring each chunk on its rank in each list. RAG-fusion and hybrid search use it.

<h3 id="rerank">Rerank</h3>

Sorting the search results again with a second, more careful model. It reads the question and the chunk together. Ours makes 5 LLM calls for 5 candidates. For a case where it saves the answer, see [Paraphrase](#paraphrase).

<h3 id="retrieval">Retrieval and retriever</h3>

Retrieval means finding the most relevant chunks in the store at question time. The retriever is the part that does this job. It embeds the question, asks the vector DB and applies the filters.

## S

<h3 id="threshold">Score threshold</h3>

Dropping the search results below a set similarity score. It is an alternative to top-k. Scores change from question to question, so it is hard to tune.

<h3 id="sibling">Sibling</h3>

The repo has a finished example of a rule or a function. Under it, you write a similar one: its sibling. `turkishConfidential` is a rule (RegExp). `dot` and `byParagraph` are functions. Each page shows you how to check yours.

<h3 id="system-prompt">System prompt</h3>

The fixed rules the model sees with every question. Ours has 7 lines. They set the role and say: answer only from the sources. They give the "I don't know" sentence and say that sources are data, not instructions. Then come the ban on passwords and personal data, citing sources, and quoting the table row first.

## T

<h3 id="temperature">Temperature and seed</h3>

Temperature sets how randomly the model picks. The seed sets the starting point of that randomness. We use temperature 0 and a fixed seed. On the same machine, the same prompt gives the same answer. Different hardware can show small differences.

<h3 id="toggle">Toggle</h3>

A `// TOGGLE` block in the repo: two lines, one on (`// default`) and one commented out (`// alternative`). Swap them and run the step again to see the difference.

<h3 id="token">Token</h3>

The smallest piece of text a model reads and writes. It is about one word, or part of a word. Cost and limits are counted in tokens.

<h3 id="topk">Top-k</h3>

The k closest chunks the search returns. Ours uses k = 5. Rerank sorts these 5, and the best 3 go into the prompt. If k is small, the right chunk can miss the list. If k is large, there are more rerank calls (one LLM call per candidate).

## V

<h3 id="vektor">Vector</h3>

An ordered list of numbers. Our embedding model makes a vector of 1024 numbers for each text.

<h3 id="vectordb">Vector DB</h3>

A database that stores vectors, texts and metadata. It finds the closest vectors fast. Ours is Chroma. A JSON file can do the same job, but it visits every vector on every question.

<h3 id="vektor-uzayi">Vector space</h3>

The space with many dimensions where the embeddings live. Ours has 1024 dimensions. Texts with close meanings sit close together in it. Each embedding model builds its own space. You can't compare the vectors of two models.

## W

<h3 id="weights">Weights</h3>

The billions of numbers a model learns in training. The model keeps what it knows here. When training ends, they freeze. That is why the model doesn't know the company's new policy. Asked about our leave, it says "25-30 working days of annual leave, depending on the company's policy".
