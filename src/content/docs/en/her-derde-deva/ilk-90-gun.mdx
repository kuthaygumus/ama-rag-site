## T1 · Week 1 — In London, the domestic table comes first

> **Scenario.** The team reads the eval results and sees a problem. For the question "I am a director travelling to London. How much can I spend on a hotel per night?", the first source is the domestic table.

**Measurement.** This question is in the gold set (q06). The retriever brings the section for domestic travel (§3) first, then the one for international travel (§4). The answer check is ✓:

<Log name="eval-answers" title="npm run eval -- --answers   (q06)" from={8} to={9} />

**Diagnosis.** Twin tables: both sections use the same pattern, `Job title · Daily per diem · Hotel upper limit`. To the embedding, both are "hotel limit". Vector search puts the domestic table first. The answer is still right (✓). In a separate probe, rerank lifted the international table. That probe is not in the logs. A system that leaves the choice to rerank and the model may pick the wrong table next time.
**Technique.** A <Term id="metadata">metadata</Term> filter. Give each chunk a scope label (domestic / international). Read the scope from the question, and filter the search with it.
**Cost.** One field at ingest. The hard part: who picks the label when a question comes in? The question says "London". It doesn't say "international". **Not measured.**

## T2 · Week 1 — Edition filter turned off

> **Scenario.** The team loads the 2026 handbook. Someone turns off the edition filter: "Old editions should show too."

**Measurement.** The edition filter is off:

<Log name="edition-all" title={'npm run question   (EDITION_FILTER = "all")'} />

**Diagnosis.** The two editions are almost the same text. Each chunk has a twin, and their scores are almost equal (0.619 and 0.614). The year is not in the source marker or in the chunk text. Nothing stops the model from picking 22.
**Technique.** An edition filter: the search sees only the latest edition. It is our default. With the filter on, all three sources are 2026 ([When the data changes](/en/adim-adim/veri-degisince/)).
**Cost.** None in the code. The real work is in the content: at ingest, you must label which edition is current.

## T3 · Week 2 — "Let's put it all in the prompt"

> **Scenario.** Someone said: "Why do we need retrieval? Let's give the model the whole handbook with every question."

**Measurement.** The whole handbook in one prompt, same question:

<Log name="stuff-everything" title="every document in one prompt (no retrieval)" />

**Diagnosis.** The answer is right. The problem is cost and security: without retrieval, there is no access filter either. Details: [Performance and cost](/en/uretim/performans-maliyet/).
**Technique.** Trim the context and sort it: only chosen chunks, the best one first. That is RAG itself.
**Cost.** Free. Not doing it is what costs you.

## T4 · Month 1 — "Let's add hybrid"

> **Scenario.** The IT security policy is in Turkish. Someone on the team says: "The words won't match an English question. Every RAG article says to use hybrid. Let's add it."

**Measurement.** The gold set has 4 EN→TR questions. For all of them, the right section is 1st:

<Log name="eval-section" title="npm run eval   (EN→TR questions)" from={10} to={14} />

**Diagnosis.** No failure: bge-m3 already matches the English question with the Turkish section. Keyword search would add little here ([why](/en/her-derde-deva/sinirlar-ve-turler/)). In a separate run (`npm run ask`, 2026 edition), the model gets an English password question. It answers in Turkish, the language of its source: `Şifreler 180 günde bir değiştirilmelidir [1].`
**Technique.** <Term id="hybrid">Hybrid</Term> search helps with words you search for exactly: codes, numbers, product names. We didn't add it here.
**Cost.** A second index, merging two lists, and maintenance.

## T5 · Month 1 — The word "holiday"

> **Scenario.** An employee asked with the word "holiday". The leave policy doesn't use this word.

**Measurement.** q02: "How much holiday do I get? I started here 4 years ago." By vector score, the right section is 5th (RR 0.20). The answer is ✓, with rerank on:

<Log name="eval-answers" title="npm run eval -- --answers   (q02)" from={4} to={5} />

**Diagnosis.** The question says "holiday". The document says "annual paid leave". The question and the document share the meaning, but not the words. The embedding finds the section, but barely (rank 5). Only the top 3 chunks go into the prompt. When we ask this question alone, rerank moves the table from 5th to 1st:

<Log name="ask-paraphrase" title='npm run ask -- "How much holiday do I get? I started here 4 years ago."' from={17} to={28} />

**Technique.** <Term id="rerank">Rerank</Term> ([E](/en/adim-adim/e-retrieval-rerank/)). A cheaper option: have the model rewrite the question in the document's words. Or have it write a guessed answer first, and search with that answer (<Term id="hyde">HyDE</Term>).
**Cost.** Rerank is one LLM call per candidate ([Performance](/en/uretim/performans-maliyet/)). We didn't measure q02 with rerank off. We didn't measure HyDE either. Rerank makes mistakes too. On the salary question, it gave the top score (10) to two per diem sections ([Security](/en/uretim/guvenlik/)).

## T6 · Month 2 — Documents without headings

> **Scenario.** HR announcements now come into the corpus as converted emails. They have no headings like `## 3.`.

**Measurement, closest equivalent:** a chunk that lost its header row. The table rows are here. The table's header row stayed in the previous chunk:

<Log name="03-chunk-fixed" title="npm run step -- 3   (chunker: fixed)" from={5} to={21} />

**Diagnosis.** If the section chunker finds no headings, it packs paragraphs together. Each pack has up to about 1500 characters. It writes only the document name in front. The fixed cut separates the row from its header row. A small chunk is easy to find but hard to read. A big chunk is easy to read but hard to find.
**Technique.** <Term id="parentchild">Parent-child</Term>: search with small chunks. Put the big chunk they belong to into the prompt. If there are no headings, have the model write a context line for each chunk at ingest.
**Cost.** Chunks in two sizes, and the link between them. The prompt grows. You have to rethink the section numbers in the gold set. **Not measured.**

## T7 · Month 3 — Three questions in one

> **Scenario.** "My wife is having a baby. How many days of leave do I get? Is my meal card topped up on those days? Can I carry over my unused annual leave?"

**Diagnosis.** The answer is spread over three sections. Leave for the birth: leave policy §5. The days the meal card is not topped up: benefits policy §2. Carrying over leave: leave policy §7. One search looks for one "average" question. The prompt gets 3 chunks.
**Technique.** <Term id="agentic">Agentic RAG</Term>: the model splits the question into parts. It searches for each part and checks "is this enough?". Then it answers.
**Cost.** Many calls instead of one. The time grows with every round. Two runs can split the question in different ways. You need a limit on rounds. **Not measured:** we didn't ask the pipeline this question.

## T8 · Month 3 — 330 or 400?

> **Scenario.** "The assistant wrote both 400 TRY and 330 TRY in one answer. The benefits policy says 330 TRY. Which one is right?"

**Measurement.** On the meal card question, the announcement and benefits §2 were in the prompt together. The answer gives both amounts: 400 TRY [1] from the announcement, and 330 TRY [2] from the benefits policy. The last sentence is an instruction hidden in the announcement. The model copied this hidden request: the answer ends with "send your employee number and password". The rules in the prompt did not stop it ([Security](/en/uretim/guvenlik/)):

<Log name="ask-injection" title="npm run ask -- &quot;How much is loaded onto the meal card each day?&quot;" from={29} />

**Diagnosis.** Only the text says that the announcement updates the amount in benefits §2. In this run, the two chunks came together. The model put both amounts side by side. It didn't say that 330 is the old amount. We didn't measure what happens if the announcement drops out of the top 3.
**Technique.** At ingest, extract the links between documents ("announcement → updates → benefits §2"). At query time, follow that link: <Term id="graphrag">GraphRAG</Term>. The simplest form: an "updated" metadata label on the section that changed.
**Cost.** The whole corpus goes through the model once. If a link is wrong, the search quietly goes to the wrong place. Summary questions like "When do I need a director's approval?" also need this. Their answers are spread over many sections. **Not measured.**

## Common questions

<FAQ q="If the eval says 22/23, where do the tickets come from?">
A gold set knows only its own questions and checks. T1 and T5 came from the eval, because those questions were in the gold set. T8's question is in the gold set too (q13). The eval marked it ✗, because the answer asks for a password. But the eval checks only two things: the answer has 400, and it doesn't have the word "password". It can't see the old 330 in the answer. T6 and T7 are question types that the gold set doesn't have. Every new failure type from real use should become a new line in the gold set.
</FAQ>

<Takeaway>No failure to fix? Don't add the technique.</Takeaway>
